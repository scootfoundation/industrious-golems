# Industrious Golems — conventions

- **State machines are explicit.** Every task runner declares its states as an enum and its transitions as a `Machine.Graph`
  (see `behavior/Machine.java`); it moves only with `machine.to(...)`, and an undeclared transition fails the game tests.
  Top-level golem behaviour is `golem/GolemMode.java`. New runners must be added to `behavior/Graphs.java`.
- **A profession decides its work in one place: a list of candidate `Job`s** (`needs/Job.java`, `Work.jobs` in `ModProfessions`), best first,
  each saying whether it is doable with the hand as it is, needs a supply fetched from the chest first (`Job.needing`, with which stacks
  will do), or waits until everything is tidy (`Job.whenTidy`). `behavior/StartTask.java` takes them in order. Do not add a second
  "what would I want" question beside the planner; a job the chest cannot supply must not hold up the ones after it. New supply/pen/stock
  situations go in the herder matrix (`herder_matrix_*` game tests; each has its own test environment so neighbouring arenas do not interfere).
- **Keep the diagram current.** After changing any graph run `tools/update-state-docs.ps1` (runs the `state_graphs` game test,
  rebuilds `docs/state-machines.html`) and republish the page as an artifact.
- Game tests: `./gradlew runGameTestServer --console=plain`.
- **Dev loop without restarts.** Run the client (`run-client.bat`), then after an edit run
  `powershell -ExecutionPolicy Bypass -File tools/hotswap.ps1` (compiles and redefines changed classes in the running game through
  by attaching to the JVM; method bodies only, a new field/method is reported as needing a restart; `-Server` targets the dev server).
  Prefer data over code for tunables: animation clips live in `assets/industriousgolems/animations/<kit|all>/<clip>.json`
  (format in `client/anim/ClipData.java`; F3+T reloads them) and chest/pick-up timings in
  `data/industriousgolems/golem_timings/<profession>.json` (`/reload`). A JSON clip replaces a code clip of the same name.
- **Keep the wiki current.** `site/` is the GitHub Pages wiki (home + one page per golem), generated by `python tools/wiki/build.py`
  (Pillow + numpy; it finds the Minecraft client jar in the Gradle cache). The golem facts live in `GOLEMS` in `tools/wiki/build.py`; the
  renders are drawn from `client/GolemModels.java` and the mod's textures, so they follow the art automatically. Whenever a change alters
  something a player can see or rely on (a golem's behaviour, range or numbers, its offerings, supplies or output, how it is built, a new
  golem or item, new art), update `GOLEMS` to match, re-run the build and commit `site/` with the change. Where a page mentions vanilla
  items or blocks use `slot(...)`, which links the Minecraft Wiki and draws the item as the inventory does. The Pages workflow deploys `site/` on push to `main`.
